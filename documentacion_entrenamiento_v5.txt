2. ADQUISICIÓN DE DATOS (de dónde salieron los datos de entrenamiento)
-------------------------------------------------------------------------------
Dataset multiclase v5:
  - Fuentes: CIC-IDS2017 + CSE-CIC-IDS2018 + CIC-DDoS2019
    (datasets académicos del Canadian Institute for Cybersecurity).
  - Carpeta de origen: datasets/CIC-IDS2017, datasets/CSE-CIC-IDS2018,
    datasets/CIC-DDoS2019.
  - Consolidado: Dataset_Limpio/dataset_global_unipaz_v5.csv
    Generado con: generador_dataset_global.py
    Total de registros: 3 738 678.
  - Clase Inyeccion_SQL: pasó de 928 a 3 108 muestras después de corregir el
    bug de encoding U+FFFD que corrompía las etiquetas de los ataques web 2017.

Dataset SQLiGuard:
  - Fuente externa: "SQL Injection Attack Netflow" (Zenodo 6907252).
  - D1_train.csv (52.7 MB): ~200 000 ataques SQLi tipo Union (MySQL/SQLServer).
    Se usa para ENTRENAR.
  - D2_test.csv (7.5 MB): 28 614 ataques SQLi tipo Blind (PostgreSQL, red
    distinta). Se usa como TEST EXTERNO independiente (nunca se vio en entrenamiento).

3. ALGORITMO Y CONFIGURACIÓN (cómo se entrenó)
-------------------------------------------------------------------------------
Modelo v5 (CEREBRO_V5.py):
  Pipeline: ImbPipeline[ StandardScaler -> SMOTE(k=5) -> CatBoostClassifier ]
  - SMOTE focalizado (sampling_strategy por dict):
      Inyeccion_SQL   -> 30 000 muestras
      Posible_Exploit -> 60 000 muestras
    Las clases masivas (Normal, DDoS...) no se tocan (evita explotar la RAM).
  - CatBoost:
      iterations          = 2000
      learning_rate       = 0.08
      depth               = 10
      task_type           = GPU
      eval_metric         = MultiClass
      od_type / od_wait   = Iter / 200 (early stopping)
      auto_class_weights  = Balanced
  - Pesos manuales por clase (mayor peso = más prioridad):
      Normal: 1.0 | DDoS_Distribuido: 1.0 | SYN_Flood: 1.2 | UDP_Flood: 1.2
      Port_Scanner: 1.5 | Posible_Exploit: 2.0 | Inyeccion_SQL: 12.0
  - Split train/test: 80/20 estratificado, random_state=42. El test se deja
    intacto (sin data leakage).
  - Tiempo de entrenamiento: ~4.8 minutos en GPU.

  Features usadas (23, estilo CICFlowMeter):
      Dst Port, Protocol, Flow Duration, Tot Fwd Pkts, Tot Bwd Pkts,
      TotLen Fwd Pkts, TotLen Bwd Pkts, Fwd Pkt Len Max, Fwd Pkt Len Min,
      Fwd Pkt Len Mean, Fwd Pkt Len Std, Bwd Pkt Len Max, Bwd Pkt Len Min,
      Bwd Pkt Len Mean, Bwd Pkt Len Std, Flow Byts/s, Flow Pkts/s,
      FIN Flag Cnt, SYN Flag Cnt, RST Flag Cnt, PSH Flag Cnt,
      ACK Flag Cnt, URG Flag Cnt.

SQLiGuard (entrenar_sqli_guard.py):
  Pipeline: Pipeline[ StandardScaler -> CatBoostClassifier ]
  - CatBoost:
      iterations    = 1500
      learning_rate = 0.08
      depth         = 8
      loss_function = Logloss
      task_type     = GPU
  - Umbral de confirmación: 0.30 (se elige bajo para maximizar recall de SQLi
    manteniendo precisión ~99.8%).
  - Features NetFlow (9):
      src_port, dst_port, protocol, flow_duration_ms, total_packets,
      total_bytes, flow_byts_s, flow_pkts_s, tcp_flags

5. UMBRALES OPERATIVOS (producción, ids.py)
-------------------------------------------------------------------------------
  UMBRAL_ML         = 0.85   -> confianza mínima para loguear y bloquear ML.
  UMBRAL_SQLI_GUARD = 0.30   -> probabilidad mínima de SQLiGuard para
                                confirmar la clase Inyeccion_SQL.
  Decisión:
    - Si SQLiGuard confirma (P >= 0.30) -> tipo_final = Inyeccion_SQL,
      confianza_ml = max(confianza_guard, confianza_v5), flag="SQLiGuard".
    - Si v5 decía SQLi pero SQLiGuard no confirma -> NO se loguea (menos
      falsos positivos).
    - Resto de clases: se loguea solo si confianza_v5 >= 0.85.
  Trazabilidad: la BD guarda confianza_ml y features_json por cada evento ML.

-------------------------------------------------------------------------------
6. LIMITACIONES CONOCIDAS
-------------------------------------------------------------------------------
  - La precisión de Inyeccion_SQL en el multiclase v5 es baja (7%) por la
    escasez de muestras reales; se mitiga con SQLiGuard.
  - Las métricas de SQLiGuard provienen de test externo (D2, Zenodo), no de
    tráfico real del campus UNIPAZ.
  - La latencia de detección -> bloqueo en red real NO se ha medido todavía.
  - El % de falsos positivos con tráfico real del campus NO se ha medido.
  - Para mayor recall de SQLi se puede bajar UMBRAL_SQLI_GUARD a 0.10
    (recall ~83% manteniendo precisión ~99.8%).
